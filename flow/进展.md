## 2026-09-18 — 构建环境连环坑：ccache 启动器导致 ninja "找不到文件"（已解决）

- **做了什么**：麦克风 slot 修复后重编，连续 6 次失败。逐个排除后定位到真因——**ccache 被当作编译器启动器**，而本机在 `python→idf.py→ninja→ccache` 这种**深层嵌套派生**时无法拉起 ccache，ninja 报 `CreateProcess failed: The system cannot find the file specified`（大量文件"编译失败"）。从 PATH 移除 ccache 目录后构建成功（`Build completed successfully`，EXIT=0，`xiaozhi.bin` 19:18 新版）。
- **为什么**：`build.py` 强制 `-DCCACHE_ENABLE=True`；只要配置阶段能找到 ccache，`build.ninja` 就会给每条编译命令加 `ccache` 前缀。ccache 仅加速、非必需，去掉无副作用。
- **怎么理解**：症状极具误导性——cinja 说"找不到文件"，但工具链、include 路径全都对。真正找不到的是 `ccache` 这个**启动器可执行**，不是编译器。而直接在前台 PowerShell 里跑 `ccache <g++> -c x.cpp` 又是**成功**的（浅层派生 OK），所以很容易误判"ccache 没问题"。
- **教育内容**：
  1. **`CreateProcess failed: The system cannot find the file specified` = ninja 拉不起命令的"第一个 token"**：先看那条命令的第一个词是谁。本题是 `ccache`。
  2. **"直接跑能成、构建里不成"→ 怀疑进程派生层级**：本机对深层嵌套的子进程创建有拦截/限制。凡是"启动器/包装器"（ccache、ccache-like、distcc…）都可能在嵌套里失效，去掉后直连编译器最稳。
  3. **判定方法**：构建失败后，`grep -c '^ccache ' <log>` 若全是 ccache 前缀命令，就去掉 ccache；成功构建的日志里不应有 ccache 前缀。
  4. **export.ps1 必须点源**：`. 'D:/.../export.ps1'`（点源）才能把 IDF_PATH/工具链 PATH 回传到当前进程；用 `& `（调用运算符）+ 管道会让环境变量丢失 → 报 "ESP-IDF version was not detected"。
  5. **venv 版本错配**：系统 `python` 是 3.13，IDF v6.1 的 venv 是 3.14；先把 venv Scripts 目录 Prepend 到 PATH，`export.ps1` 才能找到 `idf6.1_py3.14_env`。
- **产出（路径）**：`build_easyinput.ps1` 已固化三步修复（①venv 预置 ②点源 export ③移除 ccache 目录 + 必要时清 CMakeCache）。
- **问题→解决**：编不过（CreateProcess 找不到 ccache）→ PATH 去掉 ccache → 直连 g++ → 构建成功。
- **教训**：报错文本要**字面拆解到"找不到的到底是谁"**，别被"找不到文件"误导到工具链/路径长度上。

## 2026-09-18 — 语音唤醒/对话全聋：麦克风 I2S slot 用错（LEFT→RIGHT）

- **做了什么**：用户报告"喊你好小智没反应"；按键测试确认——按 S1 进「聆听中」后说话**毫无回应**，说明麦克风根本没采到声（唤醒词与对话共用同一麦，麦聋则两条全死）。逐层排查固件：唤醒词编译开关 `CONFIG_USE_AFE_WAKE_WORD=y`、模型 `CONFIG_SR_WN_WN9_NIHAOXIAOZHI_TTS=y` 嵌在 `xiaozhi.bin`、引脚 9/10/11 与官方一致、GPIO8 电源在音频前使能、待机 `idle` 也 `EnableWakeWordDetection(true)` 开麦——全正确。最终比对官方 `easy-input-maker` 固件 `prepare_microphone_channel_locked()`，发现其麦 `slot_mask = I2S_STD_SLOT_RIGHT`，而本板走 `NoAudioCodecSimplex` 8 参数构造，麦继承默认 **LEFT slot** → 读到静音。改 `InitializeAudio()` 用 10 参数构造函数、麦传 `I2S_STD_SLOT_RIGHT`（`#include <driver/i2s_std.h>`），重新编译。
- **为什么**：数字 I2S 麦克风把 PDM/I2S 数据放在 WS 的某一相位（左/右声道）上，ESP32 必须按该相位选 slot；本板麦落在 WS 高电平（右声道），用 LEFT 采到的就是静音。这是**板级实测项**，通用默认（LEFT）不适用。
- **怎么理解**：一句话——"没声音"先查 I2S 的 **slot/WS 极性**，而不是怀疑模型没加载或引脚错。本板引脚、电源、模型都对，唯一错的是"采哪一声道"。
- **教育内容**：
  1. **I2S 麦的 slot（左/右声道）是板级真值，不能套通用默认**：`NoAudioCodecSimplex` 8 参数构造默认麦用 LEFT，但有些板（含 EasyInput V2）的麦数据在 RIGHT。改法是换 10 参数构造、显式给 `I2S_STD_SLOT_RIGHT`。
  2. **官方 maker 固件是这块板的"真值表"**：`easy-input-maker/components/keyboard` + `main/platform/keyboard_audio.cpp` 里有针对本板验证过的 I2S/引脚/电源配置，遇到"板子行为不对"优先去那里比对，比猜通用默认快得多。
  3. **"全聋"类症状先二分**：按键(S1)进聆听中说话→有回应说明麦 OK（问题在唤醒词/灵敏度）；→没回应说明麦没声（硬件或 I2S 格式）。本例是后者。
  4. **排查顺序**：引脚/电源 → 唤醒词编译+模型 → 待机是否开麦 → 最后才是 I2S 格式(slot/ws_pol/bit_shift)。前三项本板都正确，所以收敛到 slot。
- **产出（路径）**：`main/boards/easyinput-v2/easyinput_v2_board.cc`：`InitializeAudio()` 改用 10 参数 `NoAudioCodecSimplex`（扬声器 `I2S_STD_SLOT_LEFT`、麦 `I2S_STD_SLOT_RIGHT`）+ `#include <driver/i2s_std.h>`。
- **问题→解决**：语音唤醒不触发 + 按键对话无回应 → 麦 I2S slot LEFT→RIGHT → **已重编重烧并在真机验证通过**。
- **验证结果（2026-09-18 19:2x，COM15 串口日志）**：✅ `Model 0: wn9_nihaoxiaozhi_tts` 加载 + `AFE Pipeline: |VAD|->|WakeNet(wn9_nihaoxiaozhi_tts)|`；✅ `Application: Wake word detected: 你好小智`；✅ `Application: >> 你好，小志。`（ASR 成功转写＝麦确实采到人声）；✅ `listening -> speaking` 对话闭环、表情 happy。**麦克风问题确认修复**。
- **顺带观察（非阻塞）**：开机早期串口出现两次 `E BOD: Brownout detector was triggered` 导致重启，随后自行稳定并正常工作。属**供电跌落**（USB 口/线供电不足），若反复出现建议换供电更强的 USB 口/线；与本次代码改动无关。
- **约束**：仅改板子目录；未动上游共享 `no_audio_codec.cc`。

## 2026-09-18 — 真机首启崩溃定位并修复（无屏板必须先 lv_init）

- **做了什么**：真机首启后板子连上 WiFi，在 `starting -> activating` 阶段必崩（`Guru Meditation ... LoadProhibited`，`EXCVADDR=0x14`，随后 `Rebooting`）。用 `xtensa-esp-elf-addr2line` 反解 ELF 的 backtrace，一次定位到源码行；在板子构造函数最前加 `InitializeLvgl()`（`lv_init()`）后重新编译通过。
- **为什么**：用户贴出实机崩溃日志；这是「无屏」这条设计约束引出的**新一类**问题——不是缺功能，而是上游代码路径依赖了显示板才会做的初始化。
- **怎么理解**：崩溃栈为 `Assets::LvglStrategy::Apply`(assets.cc:291) → `LvglCBinFont::LvglCBinFont`(lvgl_font.cc:6) → `cbin_font_create` → `lv_malloc` → `lv_tlsf search_suitable_block`，即 **LVGL 的 TLSF 分配器控制块为空指针**。`HAVE_LVGL` 默认就是 1（`main/display/display.h`：只有定义了 `CONFIG_USE_EMOTE_MESSAGE_STYLE` 才不定义），所以 `Assets` 一定走 `LvglStrategy`；而 `lv_init()` 历来只由显示驱动调用。本板没有显示驱动 → LVGL 从未初始化 → 但 `LvglStrategy::Apply` **先构造字体、后判断 display**，于是踩空。**修法**：无屏也提前 `lv_init()`。
- **教育内容**：
  1. **拿到 `Guru Meditation` 先别猜**：`xtensa-esp-elf-addr2line -pfiaC -e build/xiaozhi.elf <backtrace 各地址>` 能直接反解出「函数 + 文件:行号」，本次一轮定位。配合 `EXCVADDR` 判断性质——`0x14` 这种**小偏移量**几乎必然是空指针成员访问（null + 20 字节）。
  2. **`Board::GetDisplay()` 永远不是 nullptr**：它默认返回静态 `NoDisplay`。所以 `display == nullptr` 这类兜底分支在无屏板上**不生效**，不能拿它当"无屏保护"。
  3. **`CONFIG_USE_EMOTE_MESSAGE_STYLE` 不是"无屏开关"**：Kconfig 里它 `depends on` 仅限 5 块官方板（ESP32_S3_BOX / ESP-VOCAT / LICHUANG_DEV_S3 / RYMCU_BIGSMART / ESP-SENSAIRSHUTTLE），且会把 assets 分区切成 expression 分区——别用它绕。
  4. **"无屏"不等于"不依赖图形库"**：上层资产/字体模块可能仍走 LVGL 内存分配。裁剪类改动要顺着**调用链**核到库初始化，而不是只看板子自己的代码。
  5. 副作用与代价：`lv_init()` 会按 `CONFIG_LV_MEM_SIZE_KILOBYTES=1024` 从 PSRAM 取 1MB 池（经 `main/display/lvgl_psram_pool.h`）。本板 8MB PSRAM，可接受。
- **产出（路径）**：
  - `main/boards/easyinput-v2/easyinput_v2_board.cc`：新增 `InitializeLvgl()`（`lv_is_initialized()` 防重复）+ 构造函数首行调用 + `#include "display.h"`
  - `flow/踩坑记录.md`：新增该崩溃的完整根因/修法/复现要点
  - 构建日志：`build_v61_4.log`（`Build completed successfully`，EXIT=0）
- **问题→解决**：实机 `starting -> activating` 崩溃 → addr2line 反解定位 `lv_malloc` 踩空 → 板内提前 `lv_init()` → 重编通过（`xiaozhi.bin` 0x2380a0 = 2.22MB，app 分区 0x3f0000，余量 44%；assets 547.86K）。
- **待验证（下一棒第一件事）**：**烧录后用串口复验**——不再出现 `LoadProhibited`、能走到对话/待机；随后真机验证对话唤醒(S1)、5 颗 RGB 灯效、编码器调音量、电池读数。
- **约束**：此修复只在板子目录内，未改上游共享代码；`lv_init()` 之后无人调用 `lv_timer_handler()`（无屏无渲染循环），仅用于让资源加载可用，属预期。
